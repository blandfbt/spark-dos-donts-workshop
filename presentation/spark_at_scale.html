Scale is a parallelism problem

The same question, answered two ways
  • Spark splits data into partitions and works on all of them at once, on many cores
  • Efficient code keeps every core busy and moves as little data as possible

Partitions, stages and the shuffle

Narrow operations stream; wide operations move data
  • Narrow (filter, select, withColumn): each partition on its own, no data moves
  • Wide (groupBy, join, orderBy, window): rows with the same key must meet, so they cross the network
  • One partition = one task = one core: a window with no partitionBy runs on a single core
©2026 Databricks Inc. — All rights reserved

What serverless does for you

…and what is still up to your code

The platform handles

  • Adaptive query execution: broadcast decisions, partition sizes, skew
  • Photon: vectorized, native execution of built-in operators
  • Compute sizing and autoscaling
  • Optimized writes, auto compaction, predictive optimization

Your code still decides

  • Where the work runs: executors or one driver process
  • Whether the optimizer can see your intent
  • How often the same work is repeated
  • How data is laid out and keyed

1 · Keep the work on the executors

The driver is one machine. Anything that funnels rows through it loses the parallelism you are paying for.

DON'T
  • collect() / toPandas() on big DataFrames
  • a Python loop running one query per key
  • one INSERT per row
  • display() left in production jobs
DO
  • aggregate, filter and limit in Spark, then bring back the small result
  • one groupBy or join over all keys
  • one batch append, or MERGE INTO
  • one action (the write); row counts from DESCRIBE HISTORY
collect() 100M rows (≈ 49 GB on a 15 GB driver)
≈ 13 min→1.6 s
query per dealer ×500
≈ 7 min→0.8 s
INSERT per row ×300
≈ 6 min→1.2 s

2 · Let the optimizer see your intent

Built-in functions and declarative joins can be optimized and run in Photon. Opaque Python and giant literal lists can't.

DON'T
  • Python UDFs for arithmetic and if/else
  • withColumn in a loop over hundreds of columns
  • isin(<100k collected IDs>)
  • BETWEEN joins with no usable equality
DO
  • built-in functions (› pandas UDF › Python UDF)
  • withColumns({...}) or one select
  • a left semi join
  • the range_join hint, or a bucket key
Python UDF
≈ 120 s→1.4 s
withColumn() loop
≈ 83 s→1.0 s
range join
33 s→1.4 s

3 · Don't do the work twice

Every action re-runs the plan from the source. Every full reload re-reads all of history.

DON'T
  • count() / display() after every step
  • if df.count() > 0
  • re-reading the whole landing zone each run
DO
  • end the pipeline in one write; cache() only when you truly reuse
  • if not df.isEmpty()
  • Auto Loader or declarative pipelines (incremental)
debug actions per step
31 s→14 s
count() > 0
11.6 s→0.7 s
full reload vs Auto Loader
14 s and growing→8 s

4 · Respect the data layout

File count, file size and partitioning decide how much work every later read does.

DON'T
  • thousands of tiny files
  • inferSchema on CSV and JSON
  • partitionBy on high-cardinality columns
  • coalesce(1) before a big write
DO
  • right-sized files; OPTIMIZE / predictive optimization
  • an explicit schema, or Auto Loader schema hints
  • liquid clustering (CLUSTER BY)
  • parallel writes; aggregate first if you need one file
partitionBy(date, dealer)
≈ 23 min→13 s
coalesce(1) write
≈ 89 s→12.5 s
inferSchema
17.6 s→4.3 s

5 · Know your keys and your platform

Keys decide parallelism and correctness. Cluster-era tuning doesn't apply on serverless.

DON'T
  • Window.orderBy(...) with no partitionBy
  • joining on a key that isn't unique
  • spark.conf.set(...) tuning, sparkContext, RDDs
DO
  • Window.partitionBy(key).orderBy(...)
  • one row per key: is_current or point-in-time
  • DataFrame APIs, targeted hints; let AQE tune
window without partitionBy
≈ 41 s→7.4 s
join on SCD2 history
+100% revenue→exact

rejected→not needed
